# 多模态 RAG 农艺知识库 —— 设计说明

> 本文件是论文与答辩的素材稿，与 `README.md`（使用手册）分工不同：README 讲怎么跑，本文件讲怎么设计、怎么验证、怎么写在论文里。

## 一、模块定位

本模块是"基于改进 YOLOv8 的农作物病害检测系统"的**知识服务层**，与检测模块构成一条完整链路：

```
检测模块（改进 YOLOv8）            知识服务模块（本模块）
  图片 → 病害类别 + 病斑位置  ──→  知识检索 → 防治建议 + 参考病例图
                                        ↑
                          用户直接拍图 ──┘（以图搜病，冷启动入口）
```

它的存在解决的是研究现状评述中归纳的第三个不足：**多数研究止步于检测环节，检测结果到防治决策之间存在断层**。本模块补上"检测—诊断—处方"闭环中的后两环。

## 二、设计目标与约束

| 目标 | 具体指标 | 设计手段 |
| --- | --- | --- |
| 检索准确 | 人工标注查询集上 Hit@5 ≥ 0.85 | 中文领域编码模型 + 类别硬过滤 + 融合重排 |
| 不编造 | 建议中无可追溯来源的结论占比 = 0 | 提示词强约束 + 强制引用编号 + 药剂剂量拒答规则 |
| 可解释 | 每条建议可回溯到具体知识块 | 检索结果携带 `doc_path` / `heading` / 打分明细 |
| 可降级 | 大模型不可用时系统仍可用 | Ollama 调用失败自动降级返回检索原文 |
| 可部署 | 全流程本地运行，不依赖外部 API | 编码模型与生成模型均本地部署 |

**关键约束：数据安全与责任边界。** 药剂剂量属于高责任信息，系统的设计原则是"宁可拒答，不可编造"——提示词明确规定检索资料未涉及剂量时必须回答"请查阅当地植保部门发布的用药指导"。

## 三、总体架构

六个功能层，见 README 中的架构图与本文件附录。核心是**双链路编码 + 单点融合**：

| 层 | 输入 | 处理 | 输出 |
| --- | --- | --- | --- |
| 知识采集 | 病害文档、症状图库 | 元数据解析、类别映射 | 规范化知识条目 |
| 向量化 | 知识条目 | bge-m3 编码文本；CLIP 编码图像 | 两组归一化向量 |
| 存储 | 向量 | Chroma 持久化，余弦距离 | kb_text、kb_image 两个集合 |
| 检索 | 查询（文本 / 图像 / 检测结果） | 类别硬过滤 + 双库召回 + 加权重排 | 知识块 Top-k、参考图 Top-k |
| 上下文组装 | 检索结果 + 检测结果 | 提示词模板填充 | 受约束的提示词 |
| 生成 | 提示词 | 本地大模型生成 | 防治建议（含引用编号）+ 来源清单 |

**为什么是双链路而不是单一 CLIP。** CLIP 的文本塔在中文专业术语上的语义表达能力有限——"安全间隔期""稀释倍数""轮纹状病斑"这类词在 CLIP 的图文对齐空间里区分度低，用它检索防治文本会明显掉点；反过来 bge 系列不接受图像输入。既然两条链路的能力互补而不重叠，各自用最合适的编码器，把融合放在检索层，比强行统一编码器更合理。

## 四、数据模型

两个向量库共用 `crop_type` / `disease_id` / `disease_name` 三个元数据字段，这是"类别硬过滤"能在两库上通用执行的前提。

**kb_text（文本知识库）**

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| id | string | `{文档相对路径}::{块序号}`，确定性生成，重复入库幂等 |
| embedding | float[1024] | bge-m3 向量，L2 归一化，余弦距离 |
| document | string | 块正文，保留标题前缀以携带语义上下文 |
| doc_path / doc_title | string | 来源文档，用于引用回溯 |
| heading / section_parent | string | 所属章节与父章节 |
| doc_type / doc_type_label | string | 知识类型：symptom / cause / prevention / pesticide / management |
| disease_id / disease_name / crop_type | string | 类别元数据，检索过滤字段 |
| source | string | 知识出处 |
| chunk_index | int | 块在文档内的序号 |

**kb_image（图像检索库）**

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| id | string | `img::{相对路径}` |
| embedding | float[512] | CLIP ViT-B/32 图像向量，L2 归一化 |
| image_path / image_name | string | 图像路径与文件名 |
| disease_id / disease_name / crop_type | string | 类别元数据 |
| class_dir | string | PlantVillage 原始目录名，便于溯源 |
| in_class_index | int | 类内抽样序号 |

## 五、关键算法设计

### 5.1 章节感知的分块策略

按 Markdown 标题层级切分，超长节再以 420 字窗口、80 字重叠滑窗二次切分。两个要点：

1. **块内保留标题前缀。** 单独一个"防治措施"段落脱离标题后语义不完整，加上前缀后每个块自带上下文，短块的检索命中率明显改善。
2. **章节级知识类型。** 文档级 `doc_type` 粒度太粗——同一份病害资料里，"典型症状"是症状类、"用药参考"是用药类。因此支持在元数据中为各章节单独声明 `section_types`，三级小节自动继承其二级父节的类型。这样"只检索防治措施"这类过滤才有实际意义。

### 5.2 融合检索打分

```
score = W_DENSE · sim_dense + W_LEXICAL · sim_lexical + W_PRIOR · prior
```

| 项 | 取值 | 含义与设计理由 |
| --- | --- | --- |
| sim_dense | 余弦相似度 | bge-m3 语义匹配，负责召回语义相近但字面不同的内容 |
| sim_lexical | 查询字面覆盖率 | 查询的字符二元组原样出现在知识块中的比例。补偿向量检索对字面信息的弱敏感——"代森锰锌""嘧菌酯"这类药剂名语义相近而字面区分度高，纯向量检索容易混淆。用覆盖率而非 Jaccard 系数：查询通常只有 2～7 字，知识块数百字，Jaccard 会被文档长度稀释到接近 0（4 字查询对 300 字文档完全命中时约 0.03），权重再乘 0.25 即完全失效 |
| prior | 类别 + 类型先验 | 类别一致 +0.6，属于防治/用药/症状类文档再 +0.4。让"该病害的防治措施"排在"其他病害的相似段落"之前 |
| 权重 | 0.60 / 0.25 / 0.15 | 在 `config.py` 中集中配置，便于做权重敏感性实验 |

覆盖率对"查询词全为泛词"的情况不敏感（如查询只有"病害防治"），但本系统的查询由病害类别与检索意图程序化构造，含病害名与"防治措施""推荐药剂"等实义词，实际影响很小。这一取舍可在论文中作为方法局限如实说明。

### 5.3 以图搜病的类别投票

CLIP 图像检索返回的是单张图的相似度，直接取 Top-1 容易被单张异常样本带偏（比如某张图恰好光照异常但与查询图相似度很高）。因此先全局召回 15 张候选，再按类别聚合投票：

```
score(cls) = VOTE_MAX · max_sim + VOTE_MEAN_TOP3 · mean_top3 + VOTE_COVERAGE · (n_cls / n_max)

VOTE_MAX = 0.60   VOTE_MEAN_TOP3 = 0.30   VOTE_COVERAGE = 0.10
```

- **最高相似度**保证正确类别不会因为平均而被稀释；
- **前三均值**抑制"一张巧合相似图"造成的误判；
- **命中覆盖**反映该类别在候选集中的聚集程度——真阳性类别通常有多张相似图同时命中，而偶然命中的类别只有零星一两张。

投票分同时作为"以图搜病"入口的置信度返回给前端，低于阈值时可提示用户改用文字描述或补充拍摄。

### 5.4 提示词的约束设计

`SYSTEM_PROMPT` 中的五条规则对应五类已知失效模式：

| 规则 | 防范的失效模式 |
| --- | --- |
| 只依据检索资料作答 | 大模型用预训练知识替代系统检索结果，导致"检索形同虚设" |
| 强制标注 `[n]` 来源 | 无法追溯结论依据，答不上"这条建议从哪来的" |
| 禁止编造药剂名称与剂量 | 剂量错误可能造成药害、残留超标等实际损失 |
| 禁止"可能/大概"式模糊表述 | 病害判定环节需要明确结论，模糊表述会削弱系统的判断价值 |
| 固定五节输出结构 | 避免每次输出结构不一致，前端难以稳定渲染 |

## 六、实验与评估方案

这一部分是论文"实验与分析"章节的内容，也是本模块区别于"调个 API 就完事"的地方。

### 6.1 测试集构造

从知识库覆盖的 10 类病害中，人工编写 **50 条查询**，覆盖四种查询意图（每种约 12 条）：

| 查询类型 | 示例 | 考察点 |
| --- | --- | --- |
| 症状描述 | "叶片上褐色圆斑有同心轮纹是什么病" | 语义检索能力 |
| 防治措施 | "番茄早疫病怎么防治" | 类别过滤 + 类型先验 |
| 用药查询 | "防治马铃薯晚疫病用什么药" | 字面匹配补偿能力 |
| 以图查病 | 从测试集中抽 50 张图 | 跨模态检索能力 |

每条查询由人工标注一个"应被召回的相关知识块"集合作为标准答案。

### 6.2 评价指标

| 指标 | 定义 | 目标 |
| --- | --- | --- |
| Hit@5 | 前 5 条结果命中标准答案的比例 | ≥ 0.85 |
| MRR | 第一个正确结果排名的倒数均值 | ≥ 0.65 |
| nDCG@5 | 考虑排序位置的相关性加权 | 报告值即可 |
| 事实一致性 | 生成建议中每条结论都能在检索资料中找到依据的比例 | = 1.00 |
| 来源标注完整率 | 结论中带 `[n]` 引用的比例 | ≥ 0.95 |
| 剂量拒答正确率 | 资料未涉及剂量时正确回答"未涉及"的比例 | ≥ 0.90 |
| 单次检索延迟 | 从查询到返回 Top-5 | ≤ 500 ms |
| 单次生成延迟 | 本地 7B 模型生成完整建议 | ≤ 30 s（流式首字 ≤ 3 s） |

### 6.3 消融与对比实验

| 组别 | 配置 | 验证目标 |
| --- | --- | --- |
| A | 纯文本 RAG（仅 kb_text） | 建立基线，说明缺少图像能力的局限 |
| B | 纯 CLIP 单库（文本图像同空间） | 对照路线，验证中文文本检索能力的下降 |
| C | 双库融合（无重排） | 验证双链路的价值 |
| D | 双库融合 + 融合重排（本文方案） | 验证融合打分的贡献 |
| E | 方案 D + bge-reranker 精排 | 考察进一步优化的空间（可选） |

A/B/C/D 四组已足够支撑一组消融实验；E 组作为扩展讨论，不做也不影响结论完整性。

### 6.4 人工评分

从系统中随机抽取 30 条检测结果→建议生成的完整样本，由 3 名评分者对以下四项独立打分（5 分制），取均值并计算评分者一致性：

| 维度 | 说明 |
| --- | --- |
| 事实一致性 | 建议内容是否与检索资料一致，有无资料外内容 |
| 专业准确性 | 术语使用、防治措施的农艺合理性 |
| 可操作性 | 农户能否按建议直接操作 |
| 可读性 | 表达是否清晰、有无冗余 |

## 七、工作量与排期

| 任务 | 人日 | 说明 |
| --- | --- | --- |
| 知识文档收集与整理 | 5～8 | 10 类病害 × 6 个章节，可借助大模型起草后人工校核，但药剂部分必须人工确认 |
| 图像库准备与建库 | 1～2 | 从 PlantVillage 复制 + 等距抽样，无需额外标注 |
| 编码与检索模块开发 | 3～4 | 本模块代码已提供，主要是调参与接入 |
| 提示词迭代与生成调优 | 2～3 | 需反复测试失效模式，这部分无法压缩 |
| 测试集构造与实验 | 3～4 | 50 条查询 + 人工评分，是论文实验章节的数据来源 |
| **合计** | **14～21** | 其中约 8 人日为内容与实验工作，代码工作量较小 |

比纯文本 RAG 方案多约 5～7 人日，主要增量在图像库处理与跨模态实验。

## 八、论文写作要点

以下段落可按需改写后直接用于论文。

**研究内容一节的表述：**

> 构建图文双模态农艺知识库。文本侧整理主要作物病害的症状特征、发病规律与防治措施共五类知识条目，经章节感知分块后由 bge-m3 编码入库；图像侧收集病害典型症状图，由 CLIP 编码建立图像检索库。两库通过统一的作物与病害类别元数据关联，在检索阶段实现以类别为约束的跨模态召回。

**创新点一节的表述：**

> 提出面向农业场景的图文双库融合检索方法。针对 CLIP 文本塔在中文专业术语上语义表达能力不足、而纯文本检索又无法利用病害图像视觉信息的问题，构建文本与图像两条独立编码链路，通过类别元数据硬过滤约束召回范围，并以"向量相似度 + 字面重合度 + 类别类型先验"的加权打分完成融合重排。同时提出基于类内投票的图像检索置信度估计方法，通过最高相似度、前三均值与命中覆盖率三项加权，抑制单样本噪声导致的类别误判。

**答辩可能被问到的问题与应答方向：**

| 问题 | 应答要点 |
| --- | --- |
| 为什么不直接用一个多模态大模型？ | 系统要求可追溯——大模型直读图像无法给出"依据哪条资料"的答案；且本地 7B 视觉模型在病害细粒度识别上未必优于专用检测模型 + CLIP 检索的组合。多模态大模型作为兜底方案在本设计中列为扩展方向。 |
| 检索结果怎么证明是对的？ | 6.2 节的指标：Hit@5、MRR、nDCG@5，配 50 条人工标注查询集。 |
| 大模型编错了怎么办？ | 提示词层面强约束 + 强制引用编号 + 剂量拒答规则，配合 6.4 节的人工评分验证事实一致性。 |
| 这套方法换个作物还能用吗？ | 类别元数据驱动，扩展只需新增知识文档与图像目录并在 `class_map.py` 登记，不需要改动检索代码。 |

## 九、风险与降级方案

| 风险 | 影响 | 应对 |
| --- | --- | --- |
| 知识文档病名与检测模型类别名不一致 | 类别硬过滤全部落空，检索退化为全局检索 | 用 `class_map.py` 统一登记类别三元组；建库时对未登记或存在歧义的病名输出告警，而不是静默通过 |
| 别名歧义（"早疫病"同属番茄与马铃薯） | 静默映射到错误病害，检索出错类别知识 | 别名索引按多值集合构建，命中多个候选时拒绝自动解析（返回 None），由人工确认；`class_map.ambiguous_names()` 可列出全部歧义项 |
| 知识文档撰写耗时超预期 | 影响建库进度 | 优先覆盖 10 类检测病害即可；文档量不影响代码链路，缺失部分用 `_模板.md` 补写 |
| CLIP 在同类病害间区分度不足 | 投票结果混淆（如早疫 vs 晚疫） | 早疫/晚疫本就视觉相似，这是可如实报告的现象：对外说明"图像检索给出候选，最终判定以检测模型为准"，把图像库定位为可解释性佐证而非独立判定依据 |
| Ollama 生成延迟高 | 演示体验差 | 接口支持流式输出；演示用短提示词控制生成长度在 400 字内 |
| 显存不足 | 无法同时加载检测模型与 CLIP | bge 与 CLIP 编码可放在建库阶段离线完成，推理时只加载生成模型；或把文本编码模型换为 bge-small 版本 |
| 检索到测试集图像导致"数据泄漏"质疑 | 影响实验可信度 | 建库图像必须从训练集之外选取，并在论文中明确说明选取规则（见 `data/image_library/README.md` 末尾） |
